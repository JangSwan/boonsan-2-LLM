# 트러블슈팅 기록

구현과 실측 중에 만난 문제를 원인, 해결, 확인 순서로 남긴다. 위쪽이 실제 GPU(real 모드)에서 만난 문제이고, 아래쪽이 mock 통합 시험(CI)에서 만난 문제다.

- 환경: AWS 서울 리전 g6.xlarge(NVIDIA L4 24GB) 1대, vLLM 0.34.0, Llama-3.1-8B-Instruct
- 시각은 로그 기준 UTC다(한국 시간 = UTC + 9).

## R1. 긴 질문 1건에 정상 요청 19건이 같이 격리됨

**상황.** 실제 GPU 1대에서 동시 40건 지속 부하(QAS2 연습)를 걸어 둔 채, 웹 화면에서 "긴 입력 예시"를 보냈다.

**증상.**
- 화면: 그 질문은 "요청을 처리하지 못했습니다 (재시도 상한 도달)"로 실패했다.
- 운영자 화면: 격리(quarantined)가 1건이 아니라 **20건**이었다.
- 부하 생성기: 끝난 요청 수가 수십 초씩 멈추는 구간이 생겼다.

**조사.** worker 로그에서 `engine.failed` 이벤트를 모아 보니 5번이었고, 매번 진행 중인 요청을 통째로 잃었다.

| 시각 (UTC) | 원인 | 함께 잃은 요청 |
|---|---|---|
| 15:21:46 | 연결 오류 (R2) | 39건 |
| 15:23:14 | 긴 질문 거절 `HTTP 400` | 31건 |
| 15:23:35 | 긴 질문 재시도, 다시 `HTTP 400` | 24건 |
| 15:23:42 | 연결 오류 (R2) | 5건 |
| 15:23:46 | 연결 오류 (R2) | 1건 |

진척 보고가 끊긴 요청(`lease.renew-stopped`)은 98건이었다. 이 가운데 엔진 실패를 두 번 겪은 정상 요청이 재시도 상한(2회)에 닿아 격리됐다.

**원인.**
- `VllmEngineAdapter`는 스트림 하나라도 오류가 나면 엔진 전체 장애(`EngineFailureException`)로 처리했다.
- mock에서는 장애 주입이 곧 엔진 전체 장애를 흉내 내는 것이라 이 처리가 맞았다. 그대로 real로 가져온 것이 잘못이었다.
- 실제 엔진에서는 "이 입력만 너무 길다"처럼 **요청 하나만의 오류(4xx)**가 흔하다.

**해결** (`1bf583b`).
- 엔진 결과 `StepResult`에 실패한 요청 목록 `failedIds`를 추가했다.
- `EngineScheduler`는 그 요청만 진척 보고에서 뺀다. 그 요청은 설계(sd4)대로 lease 만료 → 재시도 → 격리로 가고, **다른 요청은 계속 생성된다.**
- 5xx나 연결 자체가 안 되는 경우만 엔진 장애로 본다.

**확인.**
- 가짜 vLLM으로 같은 상황(동시 40건 + 너무 긴 입력 1건)을 재현했다.
  - 수정 전: 엔진 장애 2회, 정상 요청까지 격리
  - 수정 후: 엔진 장애 0회, 격리는 긴 입력 1건
- 단위 테스트를 추가했다: 400은 그 요청만 실패하고 옆 요청은 끝까지 생성된다.

**배운 점.** 실패를 처리할 때는 **어디까지 영향을 줄지(blast radius)**를 먼저 정해야 한다. 재시도와 격리 장치가 설계대로 동작해도, 실패 범위를 잘못 잡으면 그 장치가 정상 요청을 해친다.

## R2. 부하 중 연결 오류로 진행 중 요청이 한꺼번에 끊김

**증상.** 긴 질문을 보내기 **전에도** `java.io.IOException: HTTP/1.1 header parser received no bytes`로 엔진 장애가 났고, 39건이 한꺼번에 끊겼다.

**원인.**
- worker(JDK `HttpClient`)는 vLLM과의 연결을 재사용한다. JDK 기본 유지 시간은 30초다.
- vLLM(uvicorn)은 쉬는 연결을 약 5초 뒤에 닫는다.
- 그래서 이미 닫힌 연결로 새 요청을 보내는 경쟁 상태가 생겼다.
- 실제 서버에 붙여야만 드러나는 종류라 mock 시험으로는 잡을 수 없었다. R1 때문에 이 오류가 엔진 전체 장애로 커졌다.

**해결** (`1bf583b`, `44716bc`).
- `-Djdk.httpclient.keepalive.timeout=3`: 연결 유지 시간을 vLLM보다 짧게 맞췄다.
- 첫 토큰을 받기 전에 끊긴 요청은 그 요청만 다시 연다. 아직 출력이 없으니 다시 보내도 안전하다. 횟수는 `llm.worker.engine.vllm-open-retries`(기본 2)로 정한다.

**확인.** 가짜 vLLM에서 연결 3%를 무작위로 끊었다. 끊긴 13건이 모두 그 요청만 다시 연결해 정상으로 끝났고, 엔진 장애는 0회였다.

**배운 점.** 연결을 재사용할 때는 클라이언트 쪽 유지 시간이 서버 쪽보다 짧아야 한다. 그리고 "다시 보내도 안전한 시점"(출력 전)을 구분해 두면 재시도를 안전하게 할 수 있다.

## R3. 답이 끝났는데 화면 연결이 10분간 닫히지 않음

**증상.** 부하 생성기가 측정 시간이 끝난 뒤에도 "진행 중 12건"에서 멈췄다. worker에서는 그 요청들이 완료로 처리돼 있었다.

**원인.**
- 재시도된 요청은 답을 처음부터 다시 만들고, 토큰 순번도 0부터 다시 센다.
- 실제 모델은 같은 질문에도 매번 답 길이가 다르다.
- 다시 만든 답이 더 짧으면, 마지막 조각(`isLast`)의 순번이 이미 보낸 순번보다 작거나 같다.
- 그러면 Front Gateway의 중복 거름(`DuplicateFilter`)이 그 조각을 버렸고, SSE가 시간 제한(10분)까지 열려 있었다.
- mock은 답 길이가 일정해서 드러나지 않았다.

**해결** (`9baddaa`). 마지막 조각이 중복으로 걸러져도 본문 없이 "끝" 표시는 보내고 SSE를 닫는다.

**확인.** `QuestionFlowTest`로 "재시도한 답이 더 짧아도 SSE가 닫힌다"를 시험한다. 같은 재현에서 끝나지 않은 요청은 1건에서 0건이 됐다.

**남은 한계.** 답을 생성하는 도중 재시도되면, 이용자는 1회차에서 받은 앞부분 뒤에 2회차 답의 나머지를 이어 받는다. 장애가 날 때만 생기는 일이라 README "알려진 한계"에 적어 두었다.

## R4. 긴 입력 예시가 엔진 한도를 넘음

**증상.** 화면에는 "약 13,200토큰"으로 표시된 긴 입력 예시가 vLLM에서 `HTTP 400`으로 거절됐다. 엔진의 요청당 최대 길이는 `--max-model-len 8192`다.

**원인.**
- 화면과 서버는 "글자 4개 = 1토큰"으로 길이를 추정했다. 영어 기준이다.
- Llama 토크나이저는 한글을 대략 한 글자에 1토큰 안팎으로 쪼갠다.
- 그래서 52,800자 예시는 실제로 수만 토큰이었다.

**해결** (`f7c34ed`).
- 예시를 보고서 기준인 약 4,000토큰(약 4,500자)으로 줄였다.
- 화면의 토큰 표시는 한글을 1글자 1토큰으로 센다.

**남은 한계.** 서버(Front Gateway)의 입력 길이 추정은 아직 "글자 수 ÷ 4"라서, 한글 질문은 크레딧 계산에서 실제보다 작게 잡힌다. 설정 `chars-per-token`으로 조정할 수 있다.

## R5. vLLM이 "하루 종일 로딩"

**증상.** `docker run`으로 vLLM을 띄운 뒤 준비 확인(`/v1/models`)이 끝없이 실패했다. 처음에는 Hugging Face 토큰이 빠진 줄 알았다.

**조사.**
- `docker ps`를 보니 만든 지 8분인데 `Up About a minute`였다. 중간에 죽었다가 다시 켜진 것이다.
- 로그를 보니 `No space left on device`였다. 디스크 100GB 중 92GB를 이미 쓰고 있었다(AMI의 CUDA 도구, vLLM 이미지, 받다 만 가중치 조각).

**원인.**
1. 디스크가 부족해서 가중치를 받다가 죽었다.
2. `--restart unless-stopped` 때문에 바로 다시 켜져서, 죽는 게 아니라 "계속 로딩"하는 것처럼 보였다.
3. 지우려 했더니 컨테이너가 좀비 상태라 `docker rm -f`도 실패했다.

**해결.**
- 받다 만 파일(`*.incomplete`, `xet` 캐시)을 정리했다.
- EBS를 100GB에서 150GB로 온라인 확장했다(`growpart`, `resize2fs`).
- 이후 컨테이너는 `--init`으로 띄워 좀비 프로세스를 막았다.
- 대기 명령은 진행 상황(디스크 사용량, 컨테이너 상태)을 출력하는 방식으로 바꿨다.

**배운 점.** 자동 재시작은 장애를 숨긴다. "오래 걸린다"고 느껴지면 먼저 재시작 횟수와 `Up` 시간을 보고, 그다음 로그에서 ERROR를 찾는다.

## R6. "하트비트 끊김" 알림을 사고 원인으로 오해

**증상.** 운영자 화면에 "worker-1 하트비트 끊김, 제외 후 lease 회수" 알림이 있었다. 그래서 "장애를 처리하는 동안 worker가 멈춰 하트비트를 못 보냈다"고 추정하고, 스케줄러 스레드 기아를 의심했다.

**조사.** 알림 시각 00:17:18(한국 시간)은 UTC 15:17:18이다. 그런데 worker 로그의 `worker.booted`는 15:17:33이었다. 알림은 사고 때가 아니라 **설정을 바꾸려고 worker 컨테이너를 다시 만든 순간**에 난 것이었다.

**결론.** 하트비트 구조는 바꾸지 않았다. 근거 없이 구조를 바꾸면 새 문제를 만들 수 있다.

**배운 점.** 여러 출처의 시각을 비교할 때는 시간대를 먼저 맞춘다. 원인을 추정했으면 고치기 전에 타임라인으로 검증한다.

## R7. QAS2 첫 토큰 지연: 크레딧의 미시작 토큰 상한

**상황.** GPU 2대(g6.xlarge, vLLM FP8 + KV FP8, 워커당 슬롯 50, 동시 실행 상한 100)로 QAS2를 쟀다. 부하 생성기 steady 모드로 동시 요청을 일정하게 유지했고, 긴 입력(약 4,000토큰)이 20% 섞였다.

**증상.** 동시 80건(상한의 80%)에서 첫 토큰 p50 3.65초, p95 4.92초였다. 3초 안에 첫 토큰을 받은 요청은 16.1%로, 기준(95%)에 크게 못 미쳤다. 실패와 섞임은 0건이었다.

**조사.**
- 부하를 낮춰 가며 쟀다(설정 변경 전).

  | 동시 요청 | GPU당 | p50 | p95 | 3초 이내 |
  |---|---|---|---|---|
  | 40건 | 20건 | 0.40초 | 0.94초 | 100% (PASS) |
  | 60건 | 30건 | 2.27초 | 3.18초 | 90.6% (FAIL) |
  | 80건 | 40건 | 3.65초 | 4.92초 | 16.1% (FAIL) |

- 40건과 60건 사이에서 첫 토큰이 갑자기 다섯 배 넘게 느려졌다. GPU가 서서히 포화되는 모양이 아니라, 어느 지점부터 대기열이 생기는 모양이었다.
- 요청별 기록(CSV)의 접수 순번을 보니, 동시 80건에서 **요청 100%가 broker 대기열에서 순번 2 이상으로 기다렸다.** 상한이 100이고 실행 중인 요청은 80건이니 원래는 바로 인출돼야 한다. 워커가 상한만큼 가져가지 않고 있었다.

**원인.**
- 워커의 크레딧은 `min(남은 슬롯, 남은 KV ÷ 요청당 KV)`이다. 단, 아직 Prefill을 시작하지 않은 입력 토큰(미시작 토큰)이 `max-unstarted-tokens` 이상이면 0이다.
- 이 상한은 GPU 안에 Prefill이 너무 쌓여 첫 토큰이 늦어지는 것을 막는 T3 장치다. 그런데 값 16000은 mock 시절에 실제 Prefill 속도를 모른 채 정한 값이었다.
- 긴 입력 4건(약 16,000토큰)만 들어와도 크레딧이 0이 되어 워커가 인출을 멈췄다. 그동안 짧은 질문까지 전부 broker 대기열에서 기다렸고, 그 대기 시간이 첫 토큰 시간에 그대로 더해졌다.

**해결.**
- 두 워커의 상한을 64000으로 올렸다. 코드는 바꾸지 않고 worker만 다시 띄웠다.
- 정식 설정으로는 `.env`의 `WORKER_MAX_UNSTARTED_TOKENS`(기본 64000)로 넣었다. `docker-compose.real-gpu.yml`과 `gpu-join.sh`가 이 값을 쓴다.
- mock 기본값(16000)은 시나리오 시험의 기준이라 그대로 두었다.

**확인.** 같은 조건으로 다시 쟀다.

| 동시 요청 | p50 | p95 | 3초 이내 |
|---|---|---|---|
| 60건 | 0.42초 | 1.02초 | 100% (PASS) |
| 80건 | 0.39초 | 1.19초 | 100% (PASS) |

동시 80건에서 p95가 4.92초에서 1.19초로 줄었다. GPU가 느린 게 아니라, 설정 때문에 GPU에 일을 덜 주고 있었다.

**배운 점.**
- 보호 장치의 문턱값은 실제 하드웨어 속도에 맞춰야 한다. mock에서 정한 숫자는 로직을 검증할 뿐, 운영값이 아니다.
- "느리다"는 결과가 나오면 먼저 **어디서 기다렸는지**(broker 대기열인지 GPU 안인지)를 데이터로 나눠 본다. 이번에는 접수 순번 하나로 원인이 갈렸다.

## 설계 가정 검증: GPU당 동시 세션 수

장애는 아니지만, 실측으로 설계 가정을 확인하고 설정을 바꾼 사례다.

보고서는 "L4 1대당 동시 생성 약 50건"을 가정했다(측정 전 추정). vLLM 시작 로그의 KV 캐시 크기를 요청당 평균 약 1,450토큰(짧은 질문 80%, 긴 입력 20%)으로 나눠 실측했다.

| 설정 | KV 메모리 | KV 토큰 수 | GPU당 동시 처리 |
|---|---|---|---|
| BF16 (U0) | 3.67 GiB | 25,600 | 약 17건 |
| 가중치 FP8 | 10.07 GiB | 77,824 | 약 53건 |
| 가중치 FP8 + KV FP8 | 10.07 GiB | 143,360 | 약 99건 |

- 원정밀(BF16)로는 가정의 3분의 1밖에 안 들어간다. 모델 축소 사다리(U1)의 FP8 단계가 왜 필요한지를 실측으로 확인했다.
- 비평에서 수용한 KV 캐시 FP8은 같은 메모리에 토큰을 약 1.8배 더 담았다.
- 운영 설정을 FP8 + KV FP8, 워커당 슬롯 50으로 정했다.
- 같은 설정에서 동시 40건 부하 중 짧은 질문의 첫 토큰은 약 0.4초였다(웹 화면 기준).

## 정리

- real에서 만난 문제(R1~R4)는 모두 **mock으로는 재현되지 않는 실제 엔진의 성질**에서 나왔다. 그 성질은 요청 하나만의 거절, 연결 유지 시간, 매번 다른 답 길이, 실제 토크나이저다. CLAUDE.md가 real 모드를 "mock으로 만들 수 없는 것을 측정할 때만 쓴다"고 정한 이유가 여기에 있다.
- 설계의 장애 대응 장치(재시도, 격리, lease 회수, 엔진 복구)는 실측 중에도 설계대로 동작했다. 문제는 그 장치를 **언제, 얼마나 넓게** 발동하느냐였고, 수정은 그 범위를 좁히는 방향으로 했다.
- 문제마다 재현 → 원인 확인 → 수정 → 같은 조건으로 재확인 순서를 지켰다. R6처럼 추정만으로 구조를 바꾸지 않았다.
